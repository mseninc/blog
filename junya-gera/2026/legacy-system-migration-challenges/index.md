こんにちは、じゅんじゅんです。

以前、稼働中のシステムを新しいシステムへ作りなおすプロジェクトに携わりました。その際、稼働中のシステム (旧システムとします) から新システムへ
データの引っ越しをする必要がありました。

初めてデータ移行を経験させていただき思ったことは「想像よりもはるかに難しいし大変」ということでした。今回はどのようなところが難しかったか、そして特に大事だと感じたところを紹介します。

## 本プロジェクトについて

本プロジェクトでは、**他社が開発・運用していたシステムを完全に新システム**として作りなおしました。

旧システムが自社で開発したものではなく、運用方法も知らない状態からのスタートです。 DB も新たに設計しなおしたため、データ構成やコード体系も変わっています。

新システムへの切り替え時にはデータ移行作業が必要だということはあらかじめわかっていました。

ただ、**今回はゼロからのシステム構築だったこともあり、どうしても最初はどうしても最初は新システムを動かすための設計・開発に集中してしまい、データ移行の準備を始めたのはプロジェクトの中盤**でした。

## データ移行方法

データ移行は以下の方法で行いました。

1. 旧 DB を新 DB と同じ環境で再現

旧 DB は MySQL、新 DB は MariaDB (O/Rマッパー に Prisma) を使用していました。

開発元からいただいた設計書をもとに旧 DB の `schema.prisma` を作成し、旧データのダンプファイルを復元しました (MariaDB は MySQL と互換性があるため、スムーズにリストアできました) 。

これで旧 DB を新 DB と同じ MariaDB で再現し、 Prisma による操作ができる状態にしました。

2. 移行用スクリプトを実行

再現した旧 DB からデータを取得 ➡ 新 DB のテーブル設計に合わせて変換 ➡ 新 DB へ登録、という 3 つの工程を行うプログラムを TypeScript で作成し、移行本番はこのスクリプトを実行するだけで完了するようにしました。

と、1 行で説明しましたが、**この 1 度しか使わない移行用スクリプトの作成が本当に大変でした**。

## 難しかった点 4 選

移行用スクリプトの作成をはじめとする準備や移行本番で特に難しいと感じたところを 4 つに分けて紹介します。

### コード体系が変更になっている

システム切り替えに伴って運用を見直した結果、マスタデータやユーザー ID などのコード体系が変更になりました。

そのため、**移行時にコード変換が必要**になり、手間が増えるだけではなく変換ミスも発生しました。

### 旧データと突き合わせることでテーブル設計の修正が生まれた

移行に伴い、**旧データと新システムのテーブル設計を突き合せた結果、その設計方法では移行できない部分に気付き**、設計の修正を余儀なくされました。

ある程度は旧システムに登録されているデータも考慮してテーブル設計しましたが、細かく確認して初めてわかるところがありました。

### 旧データに矛盾や欠落があり、個別に確認と修正が必要だった

旧データを確認した結果、以下のようなそのまま移行すべきでないデータについては個別にお客様に確認し、修正しました。

- 登録されている内容がカラム名と異なっていた
- 電話番号のような数字を想定したカラムに文字列が登録されていた
- 必須のカラムに空文字が登録されていた

また、それ以外にも以下のような不明点も発生し、つど確認することになりました。

- 捨ててもいいデータはどれか
- 新しいコード体系に当てはめたとき、このデータはどれに該当するか
- 内容の不明なデータがあるが、どういう意図のものか

### 開発環境でのリハーサルと移行後のデータの確認に時間がかかった

旧 DB を開発環境でリストアし、作成した移行スクリプトを実際に試してみてうまくいくかを確認しますが、これがなかなかエラーなく最後まで完了しません。

実行するたびにどこかでエラーが発生します。

つどスクリプトの修正、場合によっては設計を変更し、また実行しては別のエラーが出る、の繰り返しでした。

何回も修正を繰り返した結果、最後まで実行できたとしても、本当にすべて想定通りに移行できているのか確認が必要です。

これも大変で、実際本番で移行後、しばらく運用してから発覚したミスもありました。

## 大事だと思った点

### 新 DB 設計時からデータ移行を意識しておく

今回、新システムの設計はお客様からヒアリングした情報を元に進めてしまいました。

また、旧データを開発元からいただいたのがある程度設計してからだったため、旧データの内容を把握するのが後になってしまいました。

**早い段階でヒアリングした要件と照らし合わせて旧データを確認しておけば、最初から正確な設計ができていたかもしれません**。

### マッピング表を作成する

新旧システムで設計が変わっているため、「新システムのこのデータは旧システムのどのデータから持ってくるか」を 1 つずつ紐づけしたマッピング表を作成しました。

この表をもとに移行スクリプトを作成します。

テーブル数、項目数はけっして少なくなかったので、この表がないとすべての仕様を満たすスクリプトを作成するのは困難だったと思います。

### 移行期間は長めに確保しておく

データ移行はシステム切り替えと合わせて実施します。

切り替えの間、システムは使えなくなるので、何日の何時から止めるのかをお客様に決めていただき、関係者にアナウンスしていただく必要があります。

準備をしっかりするのはもちろんですが、それでも移行当日はトラブルが発生することを前提とし、お客様の確認期間も含めて 3 日間を移行期間としました。

前述のとおり、移行後に複数の不具合が発生したため、システムを使えない期間が長くなってしまうとしても、 3 日間確保しておいたことは結果的に正解でした。

## まとめ

データ移行には**「旧システムの知識」・「新システムの知識」に加え、現場担当者でしか判断できないこともあるので「業務知識」**も必要です。

この 3 種の知識を最初から備えている人はいないので、どうしてもデータ移行というものは難航するのだと思います。

少しでも完璧なデータ移行に近付けるためには、プロジェクト開始時から移行作業を意識して設計や開発を進めることが大事だと感じました。
